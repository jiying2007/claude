# Systematic Debugging

## 概述

随机修复浪费时间并制造新的 bug。快速补丁掩盖潜在问题。

**核心原则：** 在尝试修复之前**始终**找到根因。症状修复就是失败。

**违反这个流程的字面意思就是违反调试的精神。**

## 铁律

```
没有根因调查就没有修复
```

如果还没完成第一阶段，不能提出修复方案。

## 使用时机

用于**任何**技术问题：
- 测试失败
- 生产中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别要用当：**
- 时间紧迫（紧急情况使猜测变得诱人）
- "只是一个快速修复"看起来很明显
- 已经尝试了多个修复
- 之前的修复没有效果
- 不完全理解问题

## 四个阶段

必须在继续下一阶段之前完成每个阶段。

### 第一阶段：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **持续重现**
   - 能可靠触发吗？
   - 确切步骤是什么？
   - 每次都会发生吗？
   - 如果无法重现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变化可能导致这个？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing、API → service → database）：**

   **在提出修复之前，添加诊断工具：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次以收集证据，显示在哪里中断
   然后分析证据以识别失败组件
   然后调查那个具体组件
   ```

5. **追踪数据流**

   **当错误深入调用栈时：**

   - 坏值在哪里产生？
   - 什么用坏值调用了这里？
   - 一直向上追踪直到找到源头
   - 在源头修复，不在症状处修复

### 第二阶段：模式分析

**修复前找到模式：**

1. **找到工作示例**
   - 在同一代码库中找到类似的工作代码
   - 什么工作代码类似于损坏的代码？

2. **与参考对比**
   - 如果实现一个模式，**完整**阅读参考实现
   - 不要浏览——逐行阅读
   - 在应用之前完全理解模式

3. **识别差异**
   - 工作和损坏之间什么不同？
   - 列出每个差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖**
   - 这需要什么其他组件？
   - 什么设置、配置、环境？

### 第三阶段：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确说明："我认为 X 是根因，因为 Y"
   - 写下来
   - 具体，不模糊

2. **最小化测试**
   - 做**最小**可能的变更来测试假设
   - 一次一个变量
   - 不要同时修复多件事

3. **继续前验证**
   - 有效了吗？是 → 第四阶段
   - 无效？形成**新的**假设
   - **不要**在上面叠加更多修复

4. **不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 研究更多

### 第四阶段：实现

**修复根因，不是症状：**

1. **创建失败测试用例**
   - 最简单的可能重现
   - 如果可能使用自动化测试
   - 修复之前**必须**有
   - 使用 `/test-driven-development` skill 来编写正确的失败测试

2. **实现单一修复**
   - 处理已识别的根因
   - **一次**一个变更
   - 不要"顺便"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏？
   - 问题实际上解决了吗？

4. **如果修复不起效**
   - 停止
   - 计数：尝试了多少次修复？
   - 如果 < 3：带着新信息返回第一阶段，重新分析
   - **如果 ≥ 3：停止并质疑架构**
   - 在没有架构讨论的情况下不要尝试第 4 次修复

5. **3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复揭示不同地方的新共享状态/耦合/问题
   - 修复需要"大规模重构"来实现
   - 每次修复在其他地方创造新症状

   **停止并质疑基础：**
   - 这个模式从根本上是否合理？
   - 是否在"凭借惯性坚持"？
   - 是否应该重构架构而不是继续修复症状？

   **在尝试更多修复之前与用户讨论**

## 红旗 — 停止并遵循流程

如果发现自己在想：
- "现在快速修复，稍后调查"
- "只是试着改 X 看看是否有效"
- "添加多个变更，运行测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修复那个"
- "我不完全理解但这可能有效"
- "已经提出了多个修复方案（没有调查）"
- **"再尝试一次修复"（已经尝试了 2+ 次）**
- **每次修复揭示不同地方的新问题**

**所有这些意味着：停止。返回第一阶段。**

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题简单，不需要流程" | 简单问题也有根因。流程对简单 bug 很快。 |
| "紧急，没有时间走流程" | 系统化调试比猜测-检查更**快**。 |
| "先试这个，然后调查" | 第一次修复设定了模式。从一开始就做对。 |
| "之后再写测试" | 未经测试的修复不会坚持。先测试证明它有效。 |
| "一次多个修复节省时间" | 无法隔离什么有效。制造新 bug。 |
| "已经看到问题了，让我修复" | 看到症状 ≠ 理解根因。 |
| "再尝试一次"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 读错误、重现、检查变更、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |
