# Session Wrap Skill

## 概述

使用此 skill 以容易恢复的方式结束**当前**编码会话。聚焦于实际完成了什么、什么还未完成、学到了什么、以及接下来应该做什么。

## 核心规则

- 除非用户明确要求更广范围，范围是**当前会话**。
- 优先关注结果、决策、学习和后续行动，而非过程叙述。
- 不要输出按时间顺序的流水账。
- 除非有会话、git 状态或验证输出中的证据，否则不要声称工作已完成。
- 如果用户要求写文件、提交或更新文档，先总结然后确认操作。

## 工作流

### 步骤 1：确认范围

默认为当前会话。如果用户已经给出明确的收尾请求，不要额外提问。

仅在需要时澄清：
- 仅当前会话还是包含早期会话
- 是否包含提交建议
- 是否产生交接说明或只是聊天摘要

### 步骤 2：检查工作树

收集准确总结会话所需的最少证据。

推荐命令：

```bash
git status --short
git diff --stat
git log --oneline -n 10
```

如果仓库状态不可用，明确说明并用已有的会话证据继续。

### 步骤 3：总结已完成工作

按**工作流**而不是时间戳总结。

推荐结构：
- 本次完成
- 关键决策
- 涉及文件 / 模块
- 已做验证

如果没有有意义的代码变更，清晰地说明，而不是编造成果。

### 步骤 4：提取学习内容和未完成项

捕获对下一次会话重要的部分：
- 新发现
- 避免的错误或吸取的教训
- 已知风险
- 未完成任务
- 阻塞或依赖

保持此部分简洁和可操作。

### 步骤 5：提供下一步操作和提交指导

在相关时，以以下内容结束：
- 建议的下一步
- 现在是否适合提交
- 可能的提交消息方向
- 是否仍需要额外验证

不要自动提交。仅在有足够证据时才建议提交时机。

## 推荐输出格式

```markdown
## 本次会话总结

### 已完成
- ...

### 关键决策
- ...

### 涉及文件 / 模块
- ...

### 验证情况
- 已验证：...
- 未验证：...

### 经验与风险
- ...

### 下一步建议
- ...
```

## 使用时机

- 用户说"总结会话"
- 用户说"收尾"或"会话收尾"
- 当前会话已经完成一段明确工作，需要压缩成可复用总结
- 需要为下一次继续工作准备 handoff

## 不使用时机

- 用户要的是"今天所有会话"的汇总，而不是当前会话 → 使用 `/project-daily-summary`
- 用户要的是纯 commit 日报 → 使用 `/commit-daily-summary`
- 当前会话几乎没有实际工作内容，只是简单问答

## 质量清单

回应前，确认：

- [ ] 摘要范围在当前会话（除非用户要求其他）
- [ ] 已完成工作按工作流分组，不按时间线
- [ ] 验证情况如实报告
- [ ] 风险和未完成项明确
- [ ] 没有虚假完成、虚假提交就绪或虚假验证声明
