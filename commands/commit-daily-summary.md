# commit-daily-summary

## 概述

使用此 skill 将一天的 git 提交转化为可读的工作摘要。目标不是转储提交行，而是将其转换为分组的、对人类友好的任务陈述。

## 核心规则

- 默认范围是用户本地时区的**今天**，除非用户给出日期。
- 优先使用 **git 证据** 而非记忆。
- 按**工作流 / 主题**分组提交，而不仅仅按仓库顺序。
- 将原始提交消息改写为简洁的中文操作摘要。
- 不要将空的、噪音的或明显无意义的提交作为独立成就。

## 工作流

### 步骤 1：确定日期和仓库范围

默认假设：
- 日期范围：今天
- 仓库范围：当前仓库，除非用户要求多个仓库

仅在必要时澄清：
- 今天 vs 具体日期
- 当前 repo vs 多个 repos
- 用户是否只想要任务摘要还是任务摘要 + 原始提交详情

### 步骤 2：收集提交

使用带有明确仓库路径的直接 git 命令。

推荐命令模式：

```bash
git -C <repo> log --since="YYYY-MM-DD 00:00" --until="YYYY-MM-DD 23:59:59" --pretty=format:"%h%x09%s"
```

如果没有找到提交，清晰地说明。

### 步骤 3：将提交分组为工作流

将相关提交聚集在一起，例如：
- 同一功能开发
- 同一缺陷修复
- 同一配置或工具链调整
- 同一文档更新

如果几个提交显然是同一工作流的一部分，不要为每个提交创建一个任务句子。

### 步骤 4：改写为中文操作摘要

好的摘要行应该：
- 以清晰的动作动词开始
- 描述实际的业务或工程结果
- 省略嘈杂的实现琐事，除非它重要
- 对快速阅读日报的人来说是可理解的

示例：
- 实现了行情页的筛选条件持久化
- 修复了任务轮询在终态下未刷新概览的问题
- 重构了图表数据映射逻辑，降低了重复处理分支
- 补充了设置保存链路的回归测试

### 步骤 5：输出日报

推荐结构：
- 日期范围
- 今日工作摘要
- 仓库 / workstream 明细
- 如有需要，再附原始 commits

## 推荐输出格式

```markdown
## 提交总结

- 日期：2026-03-30
- 范围：today / current repo

### 今日工作摘要
- ...
- ...

### 分项明细
#### 仓库 A
- workstream 1: ...
- workstream 2: ...

### 原始提交（可选）
- abc123 feat(...)
```

## 使用时机

- 用户说"总结我今天做了什么"
- 用户说"总结我的提交"
- 用户说"提交总结"
- 用户要一份基于 commit 的日报

## 不使用时机

- 用户要的是当前会话收尾 → 使用 `/session-wrap`
- 用户要的是跨会话的项目级日报 → 使用 `/project-daily-summary`
- 用户没有 git 提交，真正需要的是工作区变更总结

## 质量清单

回应前，确认：

- [ ] 日期范围明确
- [ ] 摘要基于实际提交
- [ ] 相关提交分组为工作流
- [ ] 中文任务行对人类可读且以操作为导向
- [ ] 空噪音提交不被视为主要工作项
