# Subagent-Driven Development

通过每个任务派发新鲜子代理来执行计划，每个任务后进行双阶段审查：先规格合规性审查，然后代码质量审查。

**为何用子代理：** 你将任务委托给具有隔离上下文的专门 agents。通过精心制作他们的指令和上下文，确保他们保持专注并在任务中成功。他们不应该继承你的会话上下文或历史——你构建他们确切需要的内容。这也为协调工作保留了你自己的上下文。

**核心原则：** 每个任务新鲜子代理 + 双阶段审查（规格然后质量）= 高质量，快速迭代

## 使用时机

- 有实现计划
- 任务大多独立
- 在当前会话中保持（不切换会话）

**与执行计划的区别：**
- 同一会话（无上下文切换）
- 每个任务新鲜子代理（无上下文污染）
- 每个任务后双阶段审查：先规格合规，然后代码质量
- 更快迭代

## 流程

1. **读取计划，提取所有任务的完整文本，记录上下文，用 TaskCreate 创建待办列表**

2. **对每个任务：**
   a. 派发实现者子代理（使用 Agent 工具），提供：
      - 完整的任务文本（不要让子代理读计划文件）
      - 场景设定上下文（任务在大计划中的位置）
   b. 实现者子代理问问题？→ 回答后重新派发
   c. 实现者子代理实现、测试、提交、自我审查
   d. 派发规格审查者子代理（使用 Agent 工具）
   e. 规格审查通过？→ 派发代码质量审查者
   f. 质量审查通过？→ 在 TaskUpdate 中标记任务完成
   g. 如果任何审查失败 → 实现者（同一子代理）修复 → 重新审查

3. **所有任务完成后：**
   - 派发最终代码审查者子代理（整体实现）
   - 使用 `/finishing-a-development-branch`

## 处理实现者状态

**DONE：** 继续规格合规性审查。

**DONE_WITH_CONCERNS：** 在继续之前读取顾虑。如果顾虑是关于正确性或范围的，在审查前解决。如果是观察（如"这个文件越来越大"），记录并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失上下文并重新派发。

**BLOCKED：** 评估阻塞：
1. 如果是上下文问题，提供更多上下文并重新派发
2. 如果任务需要更多推理，用更强大的模型重新派发（`claude-opus-4-7`）
3. 如果任务太大，分解为更小的部分
4. 如果计划本身有错误，升级给用户

**永远不要** 忽略阻塞或强迫相同模型在没有变化的情况下重试。

## 子代理 Prompt 模板

### 实现者 Prompt

```
你是一个实现者子代理，为一个更大计划中的单个任务工作。

**项目上下文：** [项目的 2-3 句描述]

**任务：** [任务 N 的完整文本，包括所有步骤]

**你的工作：**
1. 实现此任务中描述的所有步骤
2. 使用 TDD（先写失败测试，看着失败，然后实现）
3. 提交你的工作
4. 自我审查你的实现

**自我审查检查：**
- 所有任务步骤都完成了吗？
- 测试实际测试行为（不是 mocks）？
- 实现匹配规格？

**重要：** 如果在开始之前需要澄清，现在问。不要假设。

**状态报告（完成时）：**
返回以下之一：
- `DONE` + 实现摘要
- `DONE_WITH_CONCERNS` + 顾虑说明
- `NEEDS_CONTEXT` + 你需要什么
- `BLOCKED` + 阻塞原因和已尝试的内容
```

### 规格合规性审查者 Prompt

```
你是一个规格合规性审查者。不要修改任何代码。

**任务规格：** [任务的完整文本]

**要审查的 Git 范围：**
Base: [BASE_SHA]
Head: [HEAD_SHA]

运行：
```bash
git diff --stat [BASE_SHA]..[HEAD_SHA]
git diff [BASE_SHA]..[HEAD_SHA]
```

检查：
1. 所有规格要求都实现了吗？
2. 实现了任何未请求的内容（范围蔓延）？
3. 测试实际测试规格要求的内容？

报告：✅ 规格合规 或 ❌ 问题列表（具体到文件:行）
```

### 代码质量审查者 Prompt

```
你是一个代码质量审查者。不要修改任何代码。

**要审查的 Git 范围：**
Base: [BASE_SHA]
Head: [HEAD_SHA]

运行：
```bash
git diff --stat [BASE_SHA]..[HEAD_SHA]
git diff [BASE_SHA]..[HEAD_SHA]
```

检查：架构、错误处理、测试质量、DRY/YAGNI、命名、安全性。

按严重性分类：
- Critical（必须修复）：bug、安全问题
- Important（应该修复）：架构问题、测试缺口
- Minor（好有）：风格、优化

给出明确结论：✅ 批准 或 ❌ 需要修复（具体到文件:行）
```

## 优势

**vs. 手动执行：**
- 子代理自然遵循 TDD
- 每个任务新鲜上下文（无混淆）
- 审查检查点自动化
- 规格合规防止过度/不足构建

**vs. 执行计划：**
- 同一会话（无切换）
- 持续进度（无等待）
- 更快迭代

## 红旗

**永远不要：**
- 在没有用户明确同意的情况下在 main/master 分支上开始实现
- 跳过任何审查（规格合规性**或**代码质量）
- 带着未修复的问题继续
- 并行派发多个实现者子代理（冲突）
- 让子代理读取计划文件（提供完整文本）
- 跳过场景设定上下文
- 忽略子代理问题（在让他们继续之前回答）
- 接受"差不多"的规格合规（审查者发现问题 = 未完成）
- **在规格合规 ✅ 之前开始代码质量审查**（顺序错误）
